# 데이터베이스 설계

2026-10-11 기준 실제 JPA 엔티티는 18개입니다. 운영·로컬 DB는 MariaDB, 격리된 자동 테스트는 H2를 사용합니다. Flyway를 활성화한 환경에는 별도의 인프라 테이블 `flyway_schema_history`가 추가됩니다.

![현재 테이블 구조](assets/db.png)

다이어그램은 [SVG 원본](assets/db.svg)과 저장소의 `scripts/render-db-diagrams.cjs`로 관리합니다. 화살표로 나열된 FK는 카드 안에 표기하며, 인수인계 이력·감사 로그의 스냅샷 식별자에는 물리적 FK가 없습니다.

## 테이블 구성

| 영역 | 실제 테이블 |
|---|---|
| 사용자·배정 | department, users, patient, shift, assignment, onboarding |
| 임상기록 | vital_sign, nursing_note, medical_orders, medication, intake_output, test_results, medical_image |
| 인수인계·지원 | handover, handover_revision, clinical_audit_log, chat_history, email_verification |

`BaseTimeEntity`를 상속하는 엔티티는 `version`, `created_at`, `updated_at`을 갖습니다. `MedicalOrder`는 해당 필드를 직접 선언합니다. 이력과 감사 로그는 별도의 기록 시각을 갖습니다. `version`은 JPA 낙관적 잠금으로 동시 수정 덮어쓰기를 방지합니다.

## 인수인계

| handover 컬럼 | 역할 |
|---|---|
| handover_id | PK |
| department_id / from_shift_id / to_shift_id / created_by | 부서·근무조·작성자 FK |
| handover_date | 기록 날짜 |
| source_type | MANUAL 또는 AI |
| status | DRAFT 또는 APPROVED |
| ai_summary | 수정 전 AI 원본, 수기는 null |
| final_summary | 사람이 편집한 초안 또는 승인본 |
| ai_model | 생성 모델, 수기는 null |
| approved_at | 승인 저장 시각 |
| version / created_at / updated_at | 동시 수정 제어와 생성·수정 시각 |

`handover_revision`은 revision_id PK, handover_id, edited_by_id/name, recorded_at, status, source_type, ai_summary, final_summary, ai_model, record_version을 보존합니다. `(handover_id, revision_id)` 인덱스로 최신 이력을 조회합니다. 작성자 이름을 복제해 당시 표시명을 보존합니다. 기존 이력에 대한 수정 API는 없습니다. 다만 DB 자체의 불변성·전자서명·장기 보존 정책까지 구현한 것은 아닙니다.

초안·승인·승인 후 수정마다 같은 트랜잭션 안에서 새 스냅샷을 저장합니다. 오래된 기존 기록은 첫 수정 직전에 이전 내용도 저장합니다. 초안은 작성자 전용이며 승인본·이력은 같은 부서에서 조회할 수 있습니다.

## 임상기록과 감사

간호기록은 표시용 HTML `content`와 AI 입력용 `plain_text`, 카테고리·중요 여부를 저장합니다. 현재 화면 검색은 조회된 목록의 프론트엔드 필터입니다. 과거 문서에 나온 Full-Text 인덱스와 CHECK 제약 예시는 현재 자동 생성 스키마에 적용됐다고 주장하지 않습니다.

투약은 `medical_order_id`로 원 처방과 연결하고 수행자·시각을 보존합니다. `clinical_audit_log`는 접근·변경 행위의 사용자·환자·리소스 식별자와 시각을 기록하며, 내용 전체 스냅샷인 인수인계 수정 이력과 구분합니다.

## 마이그레이션

운영은 Flyway 실행 후 Hibernate validate 순서입니다. 기존 DB의 최초 기준선 등록, 백업, 실패 대응은 [마이그레이션 안내](../deploy/database/README.md)를 따릅니다. `local`과 `dev`의 기본값은 validate이며 기존 스키마를 삭제하지 않습니다. 가상 데이터가 필요한 경우에만 demo 프로필을 명시적으로 사용합니다.
