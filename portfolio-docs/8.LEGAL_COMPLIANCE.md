# 보안 설계와 도입 검토 범위

2026-10-11 저장소 구현 기준입니다. MediFlow는 가상 환자로 기능을 체험하는 포트폴리오 PoC이며, 법적 적합성·EMR 인증·실제 임상 사용을 검증한 제품으로 소개하지 않습니다. 이 문서는 구현한 보호 장치와 후속 검토가 필요한 범위를 구분합니다.

## 현재 구현

| 영역 | 구현 | 검증·운영 범위 |
|---|---|---|
| 인증 | HttpOnly 쿠키 JWT, DB의 현재 역할·활성·잠금 상태 확인 | 로컬 인증·쿠키 회귀 테스트 |
| 접근 | 간호사·의사의 같은 부서 환자 접근, 처방 등록·삭제 역할 제한, 작성자 수정 제한 | 접근 서비스·오더 거부 테스트 |
| 수정 충돌 | JPA version, 간호기록·V/S·I/O·인수인계의 조회 버전 확인 | 오래된 수정 거부와 저장 버전 통합 테스트 |
| 인수인계 이력 | 수기·AI 초안, 승인, 승인 후 작성자 수정과 매 저장 스냅샷 | 별도 H2에서 재조회·승인·수정·이력 검증 |
| 투약 | 원 처방 연결, 서버 처방 기준 기록, 투약 저장과 처방 완료의 단일 트랜잭션 | 직접 수정·삭제는 원본 보존 정책상 차단 |
| 감사 이벤트 | 환자 접근, 투약 수행, 인수인계 초안 저장·승인·수정 기록 | 감사 로그 보존·위변조 방지·운영 조회 화면은 별도 과제 |
| HTML 출력 | 간호기록의 활성 콘텐츠·이벤트·이미지·링크 제거, 서식 색상 제한 | DOM 기반 공격 입력·서식 보존 테스트 |
| 외부 AI | 요청 내 환자 이름·차트번호를 가명으로 대체, 키 로그 제거, 타임아웃·응답 검증 | 자유 입력 안의 개인정보 자동 제거는 미구현 |
| 데이터베이스 | local/dev 기본 validate, prod Flyway → validate, destructive clean 차단 | 기존 DB 최초 baseline 전환 전에 백업 필요 |

공통 환자 접근 검사에서 READ 이벤트를 남깁니다. 간호기록·V/S·I/O의 수정 전후 전체 내용을 감사 스냅샷으로 남기는 기능과 전자서명은 현재 구현하지 않았습니다. 인수인계의 버전 이력과 혼동하지 않습니다.

## 환경과 데이터

로컬 개발은 HTTP와 host-only HttpOnly/Lax 쿠키를 사용합니다. 운영 설정은 Secure/None 쿠키와 HTTPS 배포 구성을 사용하지만 이번 작업에서 실제 인증서·인프라·저장 암호화 상태를 검증하지 않았습니다. 클라이언트 저장소에는 JWT를 저장하지 않습니다. 로그아웃·인증 만료 시 환자·부서 화면 상태와 진행 중 조회를 초기화합니다.

가상 데이터만 입력합니다. 이름·차트번호 가명화는 자유 텍스트·진단·기록 전체의 익명화를 의미하지 않습니다. 실제 데이터 도입 전에는 외부 AI 전송 항목·처리 위치·보존·위탁 관계와 동의 또는 적용 근거를 별도로 검토해야 합니다.

투약·임상 기록의 직접 삭제 차단은 프로젝트의 원본 보존 정책입니다. 이를 특정 법 조문에 따른 일률적인 보존기간이나 규제 충족으로 설명하지 않습니다. 기록 유형별 운영 보존기간, 백업·복원, 정정과 폐기 절차는 실제 도입 기관의 검토 범위입니다.

## 도입 전 후속 범위

- 간호기록·V/S·I/O의 정정 전후 이력과 전자서명
- 담당 환자 단위 권한, 응급 접근, 감사 로그 조회·보존·위변조 방지
- 운영 DB 암호화·백업 복원 훈련·마이그레이션 실패 복구
- 외부 AI 개인정보 처리 및 병원 데이터 연계 검토
- 실제 환경 부하·장애·임상 업무 검증과 적용되는 인증 기준 확인

세부 검증 결과는 [품질 검증 기록](10.QUALITY_AND_VALIDATION.md), 배포·DB 전환 절차는 [AWS 가이드](https://github.com/MediFlow-EMR/mediflow-dev/blob/main/deploy/aws/README.md)와 [마이그레이션 안내](https://github.com/MediFlow-EMR/mediflow-dev/blob/main/deploy/database/README.md)에 정리했습니다.
